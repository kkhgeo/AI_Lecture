# 03. 공통 패턴, 효과적인 강의 기법, 우리 강연 구성안

- 근거: 01 목록과 02 분석의 영상들. 영상 번호(E1, K2 등)는 01 문서를 따른다.
- 우리 강연의 전제: 주제는 Claude Code를 바탕으로 한 context 개념과 context engineering이다. 청중에 연구기관 연구자(비개발자 포함)가 있을 수 있다.

## 1. 여러 강의에서 반복되는 패턴

### 패턴 1. 순진한 사용에서 출발해 한 단계씩 올라가는 사다리 구조

- 가장 많이 본 구성이다. 누구나 해 본 가장 단순한 사용법을 먼저 보여주고, 그 한계를 짚고, 한 단계씩 개선한다.
- E1(Dex Horthy): 묻고 꾸짖기를 반복 → 새 창에서 다시 시작 → 의도적 압축 → 서브에이전트 → Research-Plan-Implement.
- E3(Boris Cherny): 질문하기 → 편집 → 도구 연결 → 컨텍스트 주기 → SDK → 병렬 실행.
- K13(AI싱크클럽): 23가지 팁을 기초, 중급, 고급 3단계로 묶는다.
- 효과: 청중이 자기가 지금 어느 계단에 있는지 알 수 있고, 다음에 무엇을 해 볼지가 분명해진다.

### 패턴 2. 비유 하나로 추상 개념을 고정한다

컨텍스트라는 보이지 않는 개념을 설명할 때 거의 모든 연사가 비유를 쓴다. 영상별로 모으면 다음과 같다.

| 비유 | 설명하려는 개념 | 출처 |
|---|---|---|
| 컨텍스트 창 = 작업 기억(working memory) | 모델은 대화 밖의 것을 기억하지 못한다 | E4 Karpathy, E15 Anthropic 공식 강의 |
| 영화 "메멘토"의 주인공이 문신을 읽는 장면 | 온보딩 문서(CLAUDE.md) 없이 시작하는 에이전트 | E1 Dex Horthy |
| 주방 작업대(요리와 무관한 재료가 섞이면 실수) | 관련 없는 정보가 섞인 컨텍스트 | K2 KIST 하네스 |
| 도서관 책 표지(표지만 보고 필요할 때 본문을 꺼냄) | 스킬의 메타데이터만 먼저 올리는 점진적 공개 | K3 KIST 스킬 |
| 신입사원의 오늘 업무 vs 사수 매뉴얼 전체 | 프롬프트와 컨텍스트의 차이 | K8 김플립 |
| 새로 온 인턴 온보딩 | 내 업무 맥락을 알려 줘야 일을 한다 | E16 Nate Herk |
| 엔진(모델), 자동차(하네스), 운전자(사람) | 모델, 하네스, 사용자의 역할 구분 | E16 Nate Herk |
| 터미널만 쓰는 고수 동료 | Claude Code가 무엇인지 | E2 Cal Rueb |
| 말 마구(harness) | 하네스 엔지니어링의 어원과 의미 | K2, K4 |
| 사람의 수면 중 기억 정리("dreaming") | 세션 기록을 오프라인으로 정리해 장기 메모리로 | E13 Lance Martin |

- 좋은 강의일수록 비유를 한 번 쓰고 끝내지 않는다. E4는 마무리에서 아이언맨 슈트 비유를 다시 불러오고, K8은 도입의 신입사원 비유를 결론에서 뒤집는다(모델은 시니어가 됐는데 매뉴얼은 여전히 신입용).

### 패턴 3. 주장보다 데이터와 사례로 증명한다

- E5(Jeff Huber)는 자사 실험 그래프(입력이 길수록 쉬운 작업도 성능이 떨어짐)와, 사람이 골라 준 컨텍스트가 전체 컨텍스트보다 성능이 높았다는 결과로 말한다.
- E1은 외부 연구 차트로 문제를 제기하고, 성공 사례 두 개와 실패 사례 하나를 함께 보여준다.
- K4는 같은 모델에 9달러와 200달러를 쓴 대비 실험을 제목과 첫 문장에 둔다.
- 연구자 청중에게는 이 패턴이 특히 중요하다. 주장보다 근거를 먼저 요구하는 청중이기 때문이다.

### 패턴 4. 새 용어는 계보로 소개한다

- 프롬프트 엔지니어링 → 컨텍스트 엔지니어링 → 하네스 엔지니어링 → 루프·그래프 엔지니어링으로 이어지는 흐름을 보여주는 강의가 많다(K4, K11, K12, E7, K6).
- 공통 메시지는 새 기술이라기보다 이미 하던 일에 이름이 붙었다는 것이다. 청중이 유행어에 느끼는 피로와 거부감을 줄여 준다.
- E5와 K12는 한 걸음 더 나아가 유행어 남발 자체를 비판한다. 우리 강연도 용어를 늘리기보다 개념 하나를 깊게 다루는 편이 낫다.

### 패턴 5. 청중을 움직이게 하는 장치

- 손들기 질문: E3(써 본 사람?), E6(에이전트를 몇 개 만들어 봤나, 기준을 점점 높임), E9(주장에 동의하는지 투표), E8.
- 맞혀 보기 슬라이드: E1은 차트의 y축이 무엇인지, 코드 리뷰의 목적이 무엇인지 청중에게 먼저 묻는다.
- 청중의 소재로 즉석 시연: K2는 청중에게 연구 주제를 받아 하네스 적용 전후를 비교한다. 강사가 검증할 수 있는 주제로 제한한다.
- 따라 말하기와 결과 공유: K3는 스킬 구조의 세 요소를 함께 소리 내어 말하게 하고, 참가자가 만든 결과물을 커뮤니티에 올리도록 한다.
- 따라 하기: E3는 강연 시작 때 설치 명령을 띄워 놓고 따라오라고 한다. K1은 강의 전체가 따라 하기다.

### 패턴 6. 라이브 데모 비중은 형식에 따라 양극화된다

| 형식 | 예 | 길이 | 데모 비중 | 특징 |
|---|---|---|---|---|
| 컨퍼런스 단독 발표 | E1, E5, E6, E9, E10, E11 | 11~21분 | 거의 없음 | 슬라이드, 차트, 사례 화면. 데모는 결과 화면으로 대체 |
| 공식 모범 사례 발표 | E2, E3 | 26~28분 | 낮음~중간 | 슬라이드 위주, 끝에 2~3분 라이브 또는 없음, 4분 질의응답 |
| 유튜브 튜토리얼 | K4, K5, K7, K8, K13 | 10~50분 | 중간~높음 | 챕터 세분화, 치트시트 배포, 결론 먼저 |
| 기관 실습 교육 | K1, K2, K3 | 2시간 이상 | 매우 높음 | 청중이 동시에 따라 함, 조교 배치, 질의응답 길게 |
| 라이브 코딩 워크숍 | E8 | 약 2시간 | 매우 높음 | 짜인 데모가 아님을 예고, 질문으로 방향 전환 |
| 대담·팟캐스트 | E7, E14, K12 | 35~60분 | 없음 | 진행자 질문, 슬라이드 공유 |

- 20분 안팎의 발표에서 라이브 데모를 길게 하는 사례는 거의 없었다. 짧은 발표는 결과 화면과 사례 이야기로 데모를 대신한다.
- 데모를 하는 쪽은 실패를 숨기지 않는다. E2에서는 시연 중 의도와 다른 답이 나와도 그대로 넘어가고, K1에서는 토큰 소진으로 막힌 참석자가 생긴다.

### 패턴 7. 마무리 방식

- 한 가지만 가져가라(E1): 여러 메시지를 하나로 좁힌다.
- 요약과 비유 회수(E4, K8, E10): 앞에서 쓴 틀이나 점검표를 처음부터 다시 훑는다.
- 쓸 수 있는 도구 배포: 점검표를 스킬로 만들어 공개(E10), 노션 치트시트(K5, K14), HWP 스킬과 명령어 핸드아웃(K1), 오픈소스 프롬프트(E1).
- 짧은 질의응답: 컨퍼런스형은 약 4분(E2, E3). 기관 교육은 수십 분.
- 전망과 행동 촉구: E1(팀 문화 변화), E9(사람을 루프에 더 깊게), E11(만들기는 쉬워졌지만 가치 만들기는 어렵다).

### 패턴 8. 한계와 실패를 솔직하게 말한다

- E5는 압축 문제에 대한 답이 아직 없다고 인정한다.
- E1은 실패 사례(Parquet Java)를 따로 보여주고, 40% 기준도 작업에 따라 다르다고 단서를 붙인다.
- K9(윤종희 교수)는 써 본 지 2~3주밖에 안 됐다고 먼저 밝힌다.
- 이런 솔직함이 오히려 신뢰를 높인다. 생산성을 몇 배로 올려 준다는 과장 광고에 지친 청중에게 특히 효과가 있다.

## 2. 효과적인 강의 기법 모음

1. 결과를 먼저 약속한다: 이 강의가 끝나면 무엇을 할 수 있게 되는지 첫 1분에 말한다(K7, K4, K5).
2. 목차를 30초 안에 예고한다: E2, K10.
3. 개인 경험으로 문을 연다: E2(주말 내내 빠져든 경험), E1(처음엔 별 감흥이 없었다는 고백), E6(프롬프트로 고치다 bash 스크립트로 끝난 실패담).
4. 내부 작동 원리를 먼저 보여준다: E2는 모범 사례 전에 도구와 루프 구조, 색인 없이 검색하는 방식을 설명한다. 원리를 알면 모범 사례가 암기가 아니라 추론이 된다.
5. 기억하기 쉬운 숫자 하나를 준다: 40% 경험칙(E1), 9달러 vs 200달러(K4), 시스템 프롬프트 80% 삭제(E11, E14, K8), 온보딩 2~3주 → 2~3일(E3).
6. 눈으로 보여주는 장면을 넣는다: 토큰화 도구로 대화가 실제로 어떤 모양으로 모델에 들어가는지 보여주기(E12), 성능 곡선 그래프(E5).
7. 이해를 확인하는 장치를 둔다: E9는 AI가 만든 결과물에 대해 AI가 퀴즈를 내게 하고, 통과하기 전에는 동료에게 넘기지 않는다.
8. 강연 내용을 도구로 만들어 나눠 준다: E10의 점검표 스킬, K1의 HWP 스킬.
9. 행정·환경 장벽을 미리 없앤다: K1·K2는 사전 설치 지원, 조교 배치, 요금제와 토큰 한도 안내를 강의 전에 한다.

## 3. 연구자 청중을 위해 따로 고려할 점

- 근거를 원한다: 데이터 그래프(E5)나 출처가 분명한 사례를 쓴다. 경험칙은 경험칙이라고 밝힌다.
- 예제는 연구 업무에서 고른다: 논문 요약과 번역(K1, K7), 리뷰 코멘트 반영과 리비전(K9), 보고서를 웹페이지로 바꾸기(K1), 한글 문서 처리(K1), 실험 데이터 형식 문의(K1 질의응답). 코딩 예제보다 반응이 좋다.
- 이해와 책임의 문제를 다룬다: 연구자는 AI가 만든 분석 결과에 이름을 걸어야 한다. 이해를 유지하는 방법을 다룬 E9와, 생각 자체는 AI에 넘기지 말라는 E1의 메시지가 잘 맞는다.
- 전문성에 대한 불안을 다룬다: E11은 새 모델이 주는 상실감을 강연의 한 부로 다룬다. 연구자에게는 도메인 지식이 곧 좋은 컨텍스트라는 쪽으로 풀면 긍정적으로 전환할 수 있다(E16, K7도 자기 업무를 말로 설명하는 능력이 핵심이라고 말한다).
- 보안과 신뢰: 외부 스킬을 함부로 받지 말라는 K3의 답변처럼, 연구 데이터와 권한 관리 이야기를 짧게라도 넣는다.
- 설치 장벽: 터미널이 낯선 청중이 많다. 실습을 한다면 사전 설치 안내와 현장 지원이 필수다. 강연형이라면 실습을 빼고 시연만 해도 된다.

## 4. 우리 강연 구성안

세 안 모두 같은 핵심 메시지를 공유한다. **모델은 대화창 안에 있는 것만 안다. 그러니 무엇을 넣고, 무엇을 빼고, 무엇을 파일로 남길지 설계하는 것이 context engineering이다.**

### A안. 60분 강연형: 개념, 증거, 짧은 시연 (연구기관 초청 강연)

| 시간 | 내용 | 참고 영상과 기법 |
|---|---|---|
| 0~5분 | 문제 제기: 같은 Claude인데 왜 누구는 결과가 좋고 누구는 나쁜가. 손들기로 청중 경험 확인(Claude, ChatGPT를 써 봤나? 대화가 길어질수록 답이 흐려진 경험?) | K4의 대비 도입, E3·E9의 손들기 |
| 5~12분 | 개념 1: 모델은 상태가 없다. 컨텍스트 창 = 작업 기억. 토큰화 도구 3분 시연으로 대화 전체가 하나의 긴 텍스트라는 것을 보여줌 | E4 비유, E12 시연, E6 논리 |
| 12~20분 | 증거: 입력이 길수록 성능이 떨어진다(context rot 그래프), 골라 준 컨텍스트가 더 낫다 | E5 데이터 |
| 20~35분 | Claude Code에서 컨텍스트가 만들어지는 방식: CLAUDE.md(메멘토의 문신), /context로 사용량 보기, /clear와 /compact, 서브에이전트는 역할극이 아니라 컨텍스트 격리, 스킬은 도서관 책 표지 | E2 내부 구조 먼저, E1, K3 비유 |
| 35~45분 | 시연 1회(미리 녹화본 준비): 연구 폴더(논문 PDF, 데이터, 메모)에 질문하기 → 계획 세우기 → 보고서 초안. 같은 작업을 CLAUDE.md 없이 한 번, 있을 때 한 번 비교 | E3의 질문부터 시작하기, K2 전후 비교 |
| 45~52분 | 사람의 역할: 생각을 맡기지 말 것, 계획을 읽을 것, AI가 만든 결과를 이해했는지 퀴즈로 확인 | E1, E9 |
| 52~55분 | 한 가지만 가져가기 + 비유 회수(작업대 정리) | E1 마무리, E4 수미상관 |
| 55~60분 | 질의응답 | E2·E3 형식 |

- 배포물: 연구용 CLAUDE.md 템플릿 1장, 명령어 치트시트 1장.
- 주의: 라이브 시연은 1회로 제한하고 실패에 대비해 녹화본을 준비한다.

### B안. 2시간 30분 실습형 워크숍 (연구자가 노트북을 가져오는 교육)

| 시간 | 내용 | 참고 |

## 6. 피해야 할 것

- 용어 늘어놓기: 프롬프트, 컨텍스트, 하네스, 루프, 그래프를 모두 설명하려 하면 청중이 길을 잃는다. E5와 K12가 비판하는 지점이다. 컨텍스트 하나를 깊게 다루고, 하네스는 확장 개념으로 한 슬라이드만 쓴다.
- 확인 안 된 수치: 40% 기준, 80% 삭제 같은 숫자는 출처와 조건(모델, 작업 종류)을 함께 말한다. 40%는 연사 본인이 작업에 따라 다르다고 단서를 붙인 경험칙이다.
- 긴 라이브 데모: 20~60분 강연에서 데모가 실패하면 회복하기 어렵다. 녹화본을 준비한다.
- 과장된 생산성 약속: 연구자 청중은 몇 배 빨라진다는 말보다 한계를 솔직히 밝히는 태도에 더 신뢰를 보인다(패턴 8).
