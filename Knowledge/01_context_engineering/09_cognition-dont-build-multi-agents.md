# Don't Build Multi-Agents

- **저자/기관**: Walden Yan (Cognition, Devin 개발사)
- **발행일**: 2025-06-12
- **URL**: https://cognition.com/blog/dont-build-multi-agents (구 cognition.ai 에서 리다이렉트)
- **자료 유형**: 블로그 (기업 기술 블로그)

## 핵심 요약

- 당시 유행하던 병렬 멀티에이전트 구조가 실제로는 취약하다고 비판하며, 신뢰할 수 있는 장기 에이전트를 만드는 핵심은 **context engineering**이라고 명시한 초기 글 중 하나다.
- 두 가지 원칙을 제시한다: ① 개별 메시지가 아니라 **전체 에이전트 실행 기록(trace)을 공유하라** ② **행동에는 암묵적 결정이 담겨 있고, 충돌하는 결정은 나쁜 결과를 낳는다**.
- 예: "플래피 버드 클론을 만들라"는 과제를 배경 담당, 새 담당 하위 에이전트로 나누면, 하나는 슈퍼마리오풍 배경을, 다른 하나는 스타일이 맞지 않는 새를 만들어 합치기 어려워진다. 서로의 결정을 보지 못하기 때문이다.
- 권장 구조는 **단일 스레드 선형 에이전트**. 매우 긴 작업은 행동 기록과 핵심 결정을 요약하는 별도의 **압축 모델**을 두어 해결한다.
- Claude Code의 subagent는 병렬로 코드를 쓰지 않고 명확히 정의된 질문에만 답하도록 쓰여, 이 원칙에 부합하는 예로 언급된다.

## 핵심 개념·용어 정의

- **Context sharing**: 하위 작업자가 전체 맥락(원래 과제, 앞선 결정)을 보지 못하면 잘못된 가정을 한다.
- **Implicit decisions**: 코드 스타일, 설계 선택 등 명시되지 않은 결정이 행동마다 내려진다. 병렬 작업자끼리 이것이 충돌한다.
- **Single-threaded linear agent**: 한 줄기 컨텍스트로 순차 실행해 결정의 일관성을 유지.
- **Compression model**: 긴 기록을 핵심 사건·결정 중심으로 압축하는 별도 LLM.

## 강연에 쓸 만한 포인트

- **대립 구도 슬라이드**: Anthropic "멀티에이전트로 90% 향상"(10번) vs Cognition "멀티에이전트 만들지 마라". 둘 다 옳다: 연구·검색처럼 **읽기 중심·병렬화 가능한 작업**은 격리가 이득, 코드 작성처럼 **쓰기 중심·결정이 얽힌 작업**은 공유 맥락이 중요.
- **플래피 버드 그림**: 마리오 배경 + 어울리지 않는 새 이미지 → 청중이 한눈에 "맥락 공유 실패"를 이해.
- **결론 문장**: subagent는 "일을 나눠 맡기는 동료"보다 "조사해서 요약해 오는 리서처"로 쓸 때 가장 안전하다.
- 인용(1개): "Actions carry implicit decisions, and conflicting decisions carry bad results" (Walden Yan, Cognition, 2025) — 10단어

## Claude Code와의 연결점

- Claude Code 공식 문서의 subagent 사용 지침과 일치: 결과를 요약해 돌려줄 수 있는 자기완결적 작업, 장황한 출력(테스트·로그·검색)에 subagent를 쓰고, 잦은 상호작용이나 단계 간 맥락 공유가 많은 작업은 메인 대화에서 하라고 권한다.
- 병렬 "쓰기"가 필요하면 git worktree(`isolation: worktree`)로 파일 충돌을 막고, 결과는 사람이나 리뷰 subagent가 통합.
- 실습: 같은 기능을 (a) 두 subagent가 병렬로 나눠 구현 (b) 메인 에이전트가 순차 구현, 결과의 일관성 비교.
