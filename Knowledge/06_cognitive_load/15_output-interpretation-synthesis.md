# 종합: AI 출력은 왜 해석하기 어렵고, 어떤 표현이 도움이 되나 (출력 해석 — 슬라이드용 정리)

근거 파일: 12(HCI 연구), 13(산업계 제품), 14(실무자 주장). 읽기 병목·과잉 길이는 09, 상호작용 부하 전반은 11 참고. (2026-10-01 기준)

## 1. 한 문장 결론
AI 출력이 어려운 이유는 내용이 어려워서만이 아니라 **표현이 사람에게 맞지 않아서**다(길고, 선형이고, 구조가 안 보이고, 바뀐 곳이 안 보인다). 연구자·회사·실무자 모두 같은 처방을 낸다: **같은 내용을 다른 표현으로** — 결론 먼저, 구조·그림으로, 바뀐 것만, 필요할 때 펼쳐 보기.

## 2. 왜 해석하기 어려운가 — 다섯 가지 메커니즘
| # | 메커니즘 | 무슨 일이 일어나나 | 근거 |
|---|---|---|---|
| 1 | **장황함·반복** | 짧게 물어도 길게 답하고, 후속 질문마다 앞 내용을 다시 반복한다. 아는 내용을 훑느라 시간을 쓴다. | Graphologue 형성 연구 n=10 (C1); 09 파일 YapBench |
| 2 | **구조가 안 보임** | 텍스트에 시각적 위계가 없어 어디가 핵심이고 무엇이 무엇과 연결되는지 직접 재구성해야 한다. | Graphologue P5; Karpathy 2025-06 ("텍스트는 읽고 해석하기 어렵다") |
| 3 | **선형 흐름 속에 흩어짐** | 여러 턴의 답이 한 줄로 쌓여, 앞에서 본 것을 기억 못 하고 스크롤을 반복한다. 작업 기억을 넘는다. | Graphologue (C3); Gero CHI 2024 (기준선에서 앞 응답을 잊음); Linus Lee 2022 |
| 4 | **부분을 짚어 물을 수 없음** | 답의 한 문장이 궁금해도 복사·붙여넣기로 새 질문을 써야 한다. 이해가 끊긴다. | Graphologue (C2, "정신적 부담" 진술); Canvas의 부분 선택 기능이 이 문제를 겨냥 |
| 5 | **바뀐 곳·틀린 곳이 안 보임** | 코드나 글이 통째로 다시 나오면 무엇이 바뀌었는지 비교해야 하고, 큰 변경은 검증 병목이 된다. 텍스트 추론에서는 오류도 덜 보인다. | Wattenberger 2023 (버전 간 차이 찾기); Karpathy (1,000줄 diff); Zhou 외 2025 (텍스트 CoT 오류 탐지 73.5%) |

## 3. 어떤 표현이 도움이 되나 — 근거와 함께
| 표현 | 무엇을 줄이나 | 근거(수치) | 주의 |
|---|---|---|---|
| **요약 먼저 → 상세는 펼쳐 보기**(점진적 공개) | 1, 2 | 구조화 설명이 행동까지 시간·인지 부하 감소, 단 세부 부족 불만(Wang 외 IUI 2025); Claude Code Concise 스타일(결론을 첫 문장에) | 요약만 주면 만족도가 떨어진다 → 상세를 버리지 말고 뒤로 |
| **다이어그램·개념 지도** | 2, 3 | Graphologue n=7 정성(관계 파악 쉬움); 개념 지도 n=14, 지각 부하 31.5%↓, 평가 14.1% 빨리(Han & Choi 2025) | 넓게 훑을 때는 선형이 낫다는 사람도 있음(Sensecape 6/12) |
| **위계·층위 보기** | 3 | Sensecape n=12: 탐색 개념 22.8→68.3, 위계 2.6→4.3, 재방문 0.7→12.8 | 깊이 이해 과제에서 특히 유리(9/12) |
| **여러 답 비교 화면**(하이라이트, 중복 회색) | 3, 5 | Gero n=24: 모델 비교 과제에서 차이 발견 유의하게 증가(p<0.01), 단순 선택 과제는 차이 없음 | 과제 의존적 |
| **추론을 그래프·코드로** | 5 | Zhou 외 n=125: 오류 탐지 73.5%→85.6%, 시간 64.7→57.9초 | 프리프린트 |
| **diff·시각적 검증 + 작은 단위** | 5 | Karpathy: 빨강·초록 diff로 감사, AI를 짧은 줄에(작은 덩어리로) | 통제 실험이 아닌 실무 주장 |
| **인터랙티브 설명·워크스루** | 2, 5 | Willison 2026: 애니메이션 HTML 설명, 선형 워크스루로 인지 부채 상환 | 만드는 데 시간·토큰이 든다 |
| **생성형 UI·인라인 시각화** | 1, 2 | Google 2025-11: 사람 평가에서 텍스트·마크다운보다 크게 선호(생성 시간 제외 조건); Claude 인라인 시각화 2026-03 | 생성 지연, 화려함이 정확성을 보장하지 않음 |
| **짧은 출력 요청** | 1 | 09 파일(읽기 238wpm vs 생성 속도, 과잉 길이) | 너무 짧으면 근거가 빠짐 |

## 4. Claude Code 사용자를 위한 실전 프롬프트
작업 끝 보고, 설명, 리뷰 요청에 그대로 붙여 쓸 수 있는 문장들이다.

**결론 먼저 / 길이 조절**
- "결론 먼저 한 줄, 그다음 3줄 요약, 상세는 그 뒤에."
- "5줄 이내로 답해. 더 필요하면 내가 물을게."
- "확실한 것과 추측한 것을 나눠서 표시해."

**구조로 보기**
- "표로 정리해 줘: 열은 [파일 | 무엇을 바꿨나 | 왜 | 위험]."
- "이 모듈들의 호출 관계를 Mermaid 다이어그램으로 먼저 보여 주고, 그다음 설명해."
- "데이터가 어디서 들어와 어디로 나가는지 흐름도로 그려 줘(노드 10개 이하)."

**변경 사항 검증**
- "변경 사항을 파일별로 요약해 줘. 파일마다 한 줄, 위험한 변경에는 표시."
- "diff 전체 말고, 내가 꼭 봐야 할 변경 3곳만 줄 번호와 함께 알려 줘."
- "한 번에 한 기능만 바꾸고 멈춰. 내가 diff를 확인한 뒤 다음으로 가자." (Karpathy의 '짧은 줄')

**이해 안 되는 코드**
- "이 코드를 처음 보는 사람용으로 순서대로 걷는 설명(walkthrough)을 써 줘. 코드 조각은 실제 파일에서 인용해." (Willison 선형 워크스루)
- "이 알고리즘이 한 단계씩 어떻게 움직이는지 애니메이션 HTML 페이지로 만들어 줘." (Willison 인터랙티브 설명)

**기본값으로 만들기**
- `/output-style concise` — 결론 먼저, 군더더기 제거.
- `/output-style explanatory` — 코드와 함께 `Insight`로 이유 설명(공부 중일 때).
- 커스텀 출력 스타일 또는 CLAUDE.md에 "설명은 다이어그램 먼저, 작업 보고는 파일별 표로" 같은 규칙을 넣기(공식 문서의 "Diagrams first" 예시 참고).

## 5. 슬라이드 문구 3안
1. **"문제는 내용이 아니라 표현이다"** — 같은 답도 텍스트 벽 대신 그림·표·diff로 바꾸면 더 빨리, 더 정확히 읽힌다(오류 탐지 73.5% → 85.6%).
2. **"읽지 말고 보게 하라, 다 보지 말고 바뀐 것만 보게 하라"** — 결론 먼저, 구조는 그림으로, 변경은 diff로.
3. **"AI에게 일을 시킨 뒤, 설명하는 방식도 시켜라"** — "결론 먼저 3줄", "파일별 표로", "다이어그램으로"는 모두 한 줄 프롬프트다.

## 7. 한계(강연에서 정직하게 말할 것)
- 대부분 소표본(7~24명)이거나 프리프린트·워크숍 논문이다. 대규모 통제 실험은 Zhou 외(125명) 정도.
- 코딩 에이전트 출력(긴 작업 보고·diff)을 직접 대상으로 텍스트 vs 시각 표현의 이해도를 비교한 통제 실험은 찾지 못했다. 근거는 일반 LLM 답·추론 과정 연구와 실무자 주장의 조합이다.
- 구조화는 대가가 있다: 세부 부족 불만, 생성 시간, 화려한 그림이 틀린 내용을 그럴듯하게 만들 위험.
