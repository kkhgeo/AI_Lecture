01컨텍스트

모델은 창 안에 있는 것만 안다. 그래서 무엇을 넣고, 빼고, 파일로 남길지 설계해야 한다.

  • 프롬프트는 우리가 입력한 마지막 한 줄이다. 모델이 실제로 보는 것은 그 한 줄을 포함한 창 전체다.
  • 모델은 대화 사이에 기억이 없다. 창 밖에 있는 것은 모른다고 생각하면 된다.
  • 이 챕터 질문: 창에는 무엇이 들어 있나 → 많이 넣으면 왜 나빠지나 → 그럼 어떻게 관리하나.

컨텍스트 창

아무것도 입력하기 전에, 창에는 이미 약 8천 토큰이 들어 있다

직접 확인: /context · 수치는 Claude Code 공식 문서 “Explore the context window”의 예시값 (환경 정보 280 포함, 설정마다 다름)

  • 200K 창에서 시작 직후 약 4%가 이미 차 있다. 위 막대의 검은 조각을 확대한 것이 아래 막대다.
  • 회색은 Claude Code가 넣는 것, 파란색은 우리가 쓰고 설치한 것이다. 파란 부분이 context engineering의 첫 대상이다.
  • CLAUDE.md는 매 세션 통째로 들어간다. 길게 쓸수록 매번 비용을 낸다.
  • 시연: 새 세션에서 /context → 파일 몇 개 읽기 → 다시 /context.

Context rot

창의 크기는 넣을 수 있는 양이지, 잘 쓸 수 있는 양이 아니다

방해 문장 하나

정답과 비슷한 방해 문장이 하나만 섞여도 정답률이 떨어진다.

표현이 다를수록

질문과 정답의 표현이 멀수록, 입력이 길어질 때 더 빨리 무너진다.

18개 모델

GPT-4.1, Claude 4, Gemini 2.5, Qwen3 등. 입력이 길어지면 성능이 고르게 유지되지 않았다.

출처: Hong, Troynikov, Huber (2025). Context Rot: How Increasing Input Tokens Impacts LLM Performance. Chroma Technical Report.

  • 질문: 200K, 1M 토큰 창이면 다 넣으면 되지 않나? → 이 실험이 답이다.
  • 같은 질문에 필요한 부분만 준 입력(약 300 토큰)과 전체 기록(약 113K 토큰)을 비교했다. 입력 길이만 바꾸고 과제는 같다.
  • 정확한 정답률 수치는 원문 그래프를 인용할 것(모델마다 다름). 슬라이드에는 방향만 표시했다.
  • 연결: 그래서 “많이 넣기”가 아니라 “골라 넣기”가 기술이 된다 → 다음 슬라이드.

네 가지 전략

창은 작게 두고, 나머지는 창 밖에서 관리한다

분류: Lance Martin (LangChain, 2025) “Context Engineering for Agents”의 Write · Select · Compress · Isolate. Claude Code 기능 대응은 공식 문서 기준.

  • 비유: 모델은 CPU, 컨텍스트 창은 RAM, 파일은 디스크. 운영체제가 RAM에 무엇을 올릴지 관리하듯 창을 관리한다.
  • Write: 중요한 결정과 규칙은 파일로 남긴다. compaction 뒤에도 디스크의 CLAUDE.md, memory, plan은 다시 들어온다.
  • Select: 필요할 때 필요한 것만. skills는 설명만 먼저 올리고 본문은 쓸 때 읽는다.
  • Compress: 창이 차면 요약한다. 작업이 바뀌면 /clear로 새로 시작한다.
  • Isolate: 많이 읽어야 하는 조사는 subagent에게. 메인 창에는 요약만 돌아온다.
